# Test design

## 设计要求

不能只生成 Happy Path。对目标功能按以下五类模式展开，并让每条用例有单一验证点、前置条件、数据和可观察预期：

1. **正向闭环**：覆盖完整业务流和上游单据依赖，断言最终状态；
2. **边界值**：识别数量、日期、字符长度、产能、UPH、保质期等上下边界，至少覆盖内边界、上边界、外边界；
3. **负向与校验拦截**：空必填、非法字符/注入、超报、时间冲突、重复数据、只读字段修改；
4. **状态机**：草稿→确定→锁定→关单、提交→待审→已审/驳回等转移，核验按钮可见性、禁用态和可编辑性；
5. **异常与硬件容错**：扫码重复/连击、网络延迟、接口失败、重试与告警，验证不重复提交和可恢复性。

APS 重点覆盖：销售预测→主生产计划→MRP→制造排程→出货；ERP 主数据只读；CCP、批次追溯、清洗改机、得率、多基地、委外和字段级保密。

## 用例资产契约

公司标准用例为 16 列：
`用例编号 / 级别 / 一级模块 / 二级模块 / 功能 / 验证点 / 前置条件 / 测试步骤 / 测试数据 / 预期结果 / 测试结果 / 执行人 / 执行时间 / 编写人 / 编写时间 / 备注`。

- 编号：`{SYS}_{一级模块缩写}_{二级模块缩写}_{4位序号}`，模块内连续不重号；
- 级别仅 `高级 / 中级 / 低级`；高级包含冒烟、主流程、数据权限/越权；
- 功能默认顺序：列表→查询条件设置→搜索→重置→新增→编辑→删除→导入→导出→启用→停用→规则匹配→数据权限；
- 前置条件至少写清登录、权限和数据准备；
- `testcase_json/` 是权威源，使用项目既有脚本联动导出 `testcase_xlsx/`，不直接改 xlsx。

设计输出先给出覆盖矩阵，再按用户要求生成 JSON/XLSX。材料未定义的业务规则标为待确认，不臆造。
